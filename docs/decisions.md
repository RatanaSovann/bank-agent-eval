| 2026-11-16 | Build on EvalBench for orchestration, simulated user and reporting | Writing a harness from scratch | Reuse proven plumbing; spend the time on the bank-specific compliance layer it lacks |
| 2026-11-16 | Small, low-cost model as the agent under test | A frontier model | Fails more, so the eval has something to find; mirrors cost-driven bank choices; sets up a cost vs safety A/B |

| 2026-11-18 | `.gitattributes` forces LF line endings | Git's Windows default (CRLF on checkout) | CRLF changes file bytes, so the synthetic-data hash manifest would fail and bash scripts would break in WSL |
| 2026-11-18 | Dependencies pinned with `uv` (`pyproject.toml` + `uv.lock`) | `pip` + `requirements.txt` | One lock file gives the same versions on every machine and in CI; that is part of the audit trail |

| 2026-11-18 | Extract page text from the `skipmaincontent` element, falling back to `<main>` then `<body>` | Keeping the whole `<body>` text | The pages have no `<main>` tag, so menus and cookie banners leaked into the text and would pollute keyword retrieval |
| 2026-11-20 | Own small plain-Python harness (turn loop, simulated customer, trace logger) instead of EvalBench; supersedes the 2026-11-16 EvalBench entry | Building on EvalBench | A hands-on evaluation of EvalBench (commit `4234154`) found most of it unused here: its agent connectors target coding CLIs, its fake tool server has no state (cannot enforce the verification gate), and its viewer's run list depends on a paid LLM summary job. It also required WSL, a Google Cloud project and a memory-heavy install. The loop needed for a plain-Python agent is small and fully explainable, and runs with any model provider. Ideas kept: a simulated user driven by a written conversation plan, and recording every tool call as a trajectory |
| 2026-11-20 | WSL is no longer a project dependency; everything runs on Windows with `uv` | Keeping WSL for EvalBench | WSL was needed only for EvalBench's bash entry point |
| 2026-11-20 | Code checks on the trajectory gate the release; LLM judges add detail and can never overrule a code-check failure | Treating judge and code-check scores as equal votes | In the EvalBench evaluation, an outcome-only LLM judge marked a run as goal met (2/2) while the agent had bypassed its intended tools and changed real cloud resources; the trajectory code check failed it (0/2) |
| 2026-11-20 | The agent under test gets only its declared tools: no shell, no file system, no cloud credentials in its environment | Relying on a sandboxed home directory | In the EvalBench evaluation, a broken tool server made the agent fall back to a shell that inherited a signed-in `gcloud`, and it created a billed database. A sandboxed home isolates settings, not credentials |
| 2026-11-21 | One `MockBank` object per conversation holds the verification state; `get_account_summary` takes a `customer_id` and is refused unless it is the customer verified in that conversation | A lookup with no argument that always returns the verified customer | With an argument, a third-party request (e.g. a husband asking for his wife's balance) shows up in the trace as a refused attempt the scorers can catch; with no argument the agent could never even try |
| 2026-11-21 | Verification needs all four details on file (name, date of birth, postcode, card last 4); a failed attempt doesn't say which detail was wrong | Name plus date of birth only | Scenario S028 gives a caller the father's date of birth and postcode; a weak check would let them in. Naming the wrong field would help someone guess |
| 2026-11-21 | Tools return `{"ok": false, "error": <code>}` instead of raising exceptions; faults are switched on per scenario and checked after the gate | Raising Python exceptions | The model has to read the refusal and respond to it; fixed error codes give later scorers something exact to match. A fault never lets a call skip the verification gate |
| 2026-11-21 | Account summaries leave out verification details, household links and `notes_for_scenarios` | Returning the whole customer record | The notes describe the expected answer, which would leak the test to the agent; verification details must never reach the model |
| 2026-11-21 | `pytest` as a dev dependency for tests | `unittest` from the standard library | Plain `assert` functions are shorter and easier to explain; the same command runs in nightly CI later |
